# SVG 编辑器集成可行性研究（PRD 外延需求评估）

日期：2026-09-25 ｜ 结论先行：**短期做「合规 SVG 组件库」（已内置 3 个组件），中期评估嵌入 Method Draw，不做全功能编辑器。**

## 1. 微信公众号的 SVG 支持现状（约束条件）

公众号编辑器保留**内联 SVG**（这正是大量"SVG 互动排版"玩法的基础），但有硬约束：

| 约束 | 影响 |
|---|---|
| `<style>` 标签、class/id 被剥离 | SVG 样式必须全部内联（fill/stroke 直接写在元素上） |
| 动画仅支持 SMIL `<animate>` | CSS animation 无效；`begin` 必须含 `click`（官方规则 R-1.7，PC 端无 touchstart） |
| 禁止外部资源 | 不能引用外链图片/字体；一切自包含 |
| 不支持 `foreignObject` | 无法在 SVG 里嵌 HTML |
| 尺寸与性能 | 大面积/长动画会被编辑器降级或过滤 |
| Dark Mode | SVG 内容不做转换（官方 R-4.4），深色下需自测 |

我们的引擎已经把这五条做成了 normalizer/validator 规则（R-1.7/R-2.x/R-3.1/R-4.4），SVG 组件过一遍 `pipeline()` 即可保证合规——这是 wxwright 做这件事的差异化优势。

## 2. 主流实现方式调研

| 方案 | 代表 | 优点 | 缺点 | 集成成本 |
|---|---|---|---|---|
| 成熟开源编辑器嵌入 | Method Draw / SVG-Edit（ISC/MIT） | 功能完整（节点编辑/路径/图层），iframe 嵌入即可 | 产物需深度清洗才能进公众号；体积 ~1MB；交互风格与 wxwright 极简不统一 | 中 |
| 白板画布型 | Excalidraw / tldraw | 手绘风、生态活跃 | 面向图表/白板而非排版动效；React 栈重 | 高 |
| 模板组件库（所见即所得参数化） | 135编辑器 SVG 区 / 小岛 SVG（商业闭源） | 用户零学习成本，产物天然合规 | 灵活性低于自由编辑 | 低 |
| 自研轻量编辑器 | — | 完全可控 | 工程量巨大，ROI 极低 | 极高 |

## 3. 评估结论

- **v1.x（已实现）**：内置「SVG 组件库」——预置 3 个经过规则校验的动效组件（闪烁引导按钮、描边绘制卡、渐显标语），一键插入文章，走同一条 normalizer/validator 链路。商业工具验证了"参数化组件"是该场景的主流形态。
- **v1.5（候选）**：嵌入 Method Draw iframe 作为高级面板，导出时强制经过 `pipeline()` 清洗（font-family 剥离、begin 修补 click、class/id 去除），不合规则阻断并给出原因。工作量约 3-5 天，风险在产物清洗的边界情况。
- **不做**：自研通用 SVG 编辑器。理由：该需求本质是低频高级操作，组件库 + 编辑器二段式已覆盖 90% 场景。

## 4. 组件规范（新增组件的验收标准）

1. 全内联样式，无 class/id/外部资源；
2. 动画只允许 `<animate>`/`<animateTransform>`，`begin` 必须为 `touchstart; click`（引擎自动修补，但仍建议原生写对）；
3. 宽度 100% 或固定宽度 + `data-ignore-width` 豁免；
4. 插入后 `wxwright validate` 零阻断；
5. 移动端与 Dark Mode（R-4.4 警告）人工目检。
