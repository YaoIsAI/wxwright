wxwright 全面评估报告

一份对「一条 Markdown，多渠道分发」引擎的诚实体检：哪些能力是真护城河、哪些是 PRD 承诺与代码之间的真空区、以及你最关心的「AI 自主排版 + 主动推送 + 跨平台零失真」到底能不能做成、要怎么做成。

基线 HEAD 96c0bd9 版本 v0.10.0 评估日 2026-09-27 代码量 8,546 行 Rust + 前端 3 JS 测试 114 例（4 例 live ignored） 方式 只读静态审查，未构建

01执行摘要

一句话结论

wxwright 的引擎层是真实力、产品层是半成品。核心规范引擎、单二进制性能、CLI/MCP 一等公民这三条护城河站得住；但「7 平台分发」实际只有 1 个平台能投递，「AI 自主排版」在代码层面被静默阉割到只剩配色和标题——这不是能力不足，是契约错位，而且是可以很快修好的。

五个最重要的发现

P0-1 AI 排版被静默丢弃 已亲自核实

AI 提示词明确允许模型定义 card_note / card_tip / card_keypoint 等 7 种卡片角色，但渲染器 render_card 算出角色后在第 898 行写了 let _ = role; —— 直接丢弃，全程只读调色板。同理 base_leaf（第 423 行）也丢弃 role，硬编码 paragraph_leaf。实际生效的角色只有 h1..h5 和 paragraph_leaf 三种。

证据：gui/src-tauri/src/ai.rs:748-749 ｜ crates/wxwright-core/src/render.rs:74, 423, 500, 845, 898

P0-2 AppSecret 会明文进错误信息 已亲自核实

wxwright-mp 把 AppSecret 和 access_token 拼进 URL query，出错时用 ureq_err 转字符串。而 ureq 2.12.1 的 Error::Status 的 Display 实现是 write!(f, "{}: status code {}", response.get_url(), status) —— 完整 URL 含 query。任何 4xx/5xx（代理、WAF、CDN 都可能触发）就会把密钥打进 CLI stdout/JSON 和 GUI toast。这违反 PRD §5.6「错误信息一律脱敏」。

证据：crates/wxwright-mp/src/lib.rs:181-189, 332-361, 412-414 ｜ ~/.cargo/.../ureq-2.12.1/src/error.rs:211-214

P1-1 多渠道只是 GUI 的单人秀 已亲自核实

CLI convert 没有 --platform，MCP 的 7 个工具全是微信向，全仓 grep 显示 CLI 与 MCP 从未调用过 render_caption / render_plain_html / export_kind。而 PRD 的定位是「Agent 时代的排版基础设施」——Agent 主链路看不到小红书和知乎。

P1-2 前端缓存版本漂移 3 处 已亲自核实

违反项目自己的架构铁律 5。app.js?v=24 定于 6c976cc，但 app.js 在更晚的 96c0bd9 又被改过；pet.js / ai-jobs.js 的 v=19 定于 6eabc69，之后 5f18ef0 又改了这两个文件。这正是 AGENTS.md 第 6 条踩坑的复发。

P1-3 无人值守链路缺退出码 已亲自核实

wxwright doctor 算出了 problems 变量，却恒定 Ok(0)，且完全不检查 AI Provider。CI/SCP 场景下无法用它做前置门禁。另有 7 个已注册但前端从不调用的命令（ai_complete / ai_generate_svg / ai_generate_theme / ai_image / comfy_txt2img / comfy_img2img / validate_md），是双运行时并存的遗留。

值得肯定的地方

core 零 unsafe、生产路径零 unwrap；58 个 Tauri 命令零漏注册（集合差集核验）；i18n 双语 225 键完全对齐；HTML 零重复 id；[hidden] 守卫在位；全部 JS 过 node --check；CI 真的在跑官方 puppeteer 校验器（ci.yml:44-52）；CLI 的 I-03 剪贴板阻断真实存在（main.rs:580-606）；海报自包含门禁真实实现（jobs.rs:377-422）。这套代码的「克制」不是装出来的。

如果把 PRD 里明确写成「P0 / 承诺 / 声称已交付」的条目逐条对照代码，兑现率大约在 六成。最刺眼的三个数字：真实分发能力 1/7 平台、AI 排版自由度 3 个角色 / 声称 11 个、性能 SLO 门禁 0/7 项进 CI。这不是「做得不好」，是文档跑在了代码前面——对一个要开源的、以「工程承诺」为信任状的项目，这是最该优先处理的一类债。

  • render.rs:235-420185 行 SVG 图表几何硬编码在方言渲染器内，配色 CHART_PALETTE 与标题色写死→深色主题下图表永远是浅色底，与 wrap_document 的画布逻辑不一致。

专家二 · 微信合规与零失真排版官方规范 / Dark Mode
6.0

规则元数据层是真表——20 条 ID 在 validator 里全部有对应检测代码，不存在「登记了却永不触发」的死规则。但校验能力窄于自身声明：HYGIENE 声称管 class/id/事件属性，validator 只查了危险标签名。真正的短板在主题系统，AI 提示词教模型写的角色，渲染器根本不认。

  • render.rs:74, 423, 500, 845, 898主题 blocks 只在 css() 被查询，而 css() 的 role 实参只有 paragraph_leaf 和 h1..h5；render_card 第 845 行算出 role 后第 898 行 let _ = role; 直接丢弃→AI 产出的卡片/段落覆盖 100% 被静默忽略，且 validate_generated_theme 不会报错。
  • validator.rs:63-81HYGIENE 元数据（rules.rs:168-174）声明「不含 class/id 与事件属性」，但 validator 只匹配 script/style/iframe/form 等标签名→class/id/on*/javascript: 仅由 normalizer 剥离，校验器看不见，等于「能修不能测」。

  • main.rs:582-587剪贴板阻断条件是 (inlined && !mmbiz) || data:，而 img.rs:143 把 http:// 与 https:// 同等放行且不置 inlined→明文 http 图绕过阻断，与 PRD I-03「微信可拉取的 https」不符。
  • commands.rs:96-97, 121GUI copy_rich 固定 ImageMode::Keep + base_dir: None，本地相对路径读失败只置 warning、inlined=false→不被阻断，退化成「[图片缺失]」占位块，用户粘贴后才发现。

  • rules.rs / PRD.md:282官方 R-4.1.3（纯装饰渐变豁免）在 PRD 有行、rules.rs 无此 ID；R-4.2 只查 section/div/p/span，img/table/a 漏网；display:none / visibility / z-index / float / @media 零检测。

关于「AI 动态排版」的可行性判断

当前主题系统的表达力天花板 = 全局配色 + 标题/段落行内排版。它无法表达：块级版式差异（引用是否卡片化、代码是否带行号栏）、内容感知选择（「长表格改横向滚动」「短引用改居中大字」）、条件样式（「首段放大」）、多套备选版式与局部覆盖。要达成 AI 自由版式，至少需要五层能力——详见本报告 核心问题二。

04核心问题深析

这一节正面回答你提出的每一个问题。每个问题给：现状判定 → 根因（带证据） → 方案 → 验收标准。

问题一 · 各平台「发文不同样式」到底怎么解决 方向对，但只接通了一个平台
现状判定

架构思路完全正确：把「平台差异」抽象成三件套——预览形态 / 合规规则表 / 导出物，然后让 PlatformSpec 当描述符。这是对的做法，也确实是这个项目最值钱的架构决策。

但只兑现了 GUI 一条路径。CLI 没有 --platform，MCP 7 个工具全是微信向，全仓 grep 显示 CLI 与 MCP 从未调用过 render_caption / render_plain_html / export_kind。

根因
  • platform.rs:175-182 export_kind 用 id 字符串 match，platform.rs:308 validate_platform_caption 写死 if platform != "xhs" —— 「描述符是数据不是行为」只对结构体成立，行为仍按 id 分叉。新增平台要在 6 处改代码，而不是改数据。
  • platform.rs:152 get_platform 对未知 id 静默回退 WECHAT，无告警。frontmatter 打错一个字，整篇按微信方言渲染，用户完全无感。
  • 规则表只有微信（R-1~R-4）和小红书（XHS-1..5）两套，知乎/Meta/X/LinkedIn 是空的。
方案：把行为也收进描述符
  1. 给 PlatformSpec 加行为字段：export_kind: ExportKind、caption_rules: &'static [CaptionRule]、renderer: RenderTarget。让 export_kind() 和 validate_platform_caption() 读字段而不是 match id。这样新增平台从「改 6 处代码」降到「加 1 个 const + 1 条注册」。
  2. get_platform 返回 Result 或带 fallback_warning，让「平台名打错」这件事可见。GUI 顶栏弹提示，CLI 输出 warn。
  3. CLI 加 --platform，convert / copy / validate 都支持；非 TTY 的 JSON 输出里带 platform 字段。
  4. MCP 加 wxwright_export 工具：入参 {markdown, platform, theme}，返回该平台的制品（微信=方言 HTML / 小红书=文案+图组清单 / 知乎=Markdown）。这是让 Agent 真正能用上多渠道的唯一办法。
  5. 补齐知乎规则表（宽松，但至少要有标题长度、代码块、图片域名提示），让「7 平台」里至少 3 个有真实规则。
验收标准
  • wxwright convert a.md --platform xhs --json 输出小红书文案而非微信方言；
  • MCP 的 tool_surface_matches_agent_card 漂移测试覆盖新工具；
  • 新增第 8 个平台只改 1 个 const + 1 行注册（用一次真实演练证明）。
问题二 · 让「丰富程度由 AI 排版决定」而不是固定布局（最关键） 技术上完全可实现，当前被一个 let _ = role; 卡死
现状判定

这是你诉求里最核心的一条，也是目前最可惜的一条。AI 生成主题的功能是真的（ai_generate_theme + TOML 清洗 + 校验回喂重试），但它的实际作用范围被压缩到只剩「配色 + 标题字号 + 段落行内样式」。

根因：契约错位（已亲自核实）

AI 提示词（ai.rs:748-749）告诉模型：role 可以取 h1/h2/h3/paragraph/card_note/card_tip/card_important/card_warning/card_caution/card_comment/card_keypoint。

但渲染器里 theme.blocks 只在 css()（render.rs:74）被查询，而 css() 的调用点只有两处：

  • render.rs:425 —— 硬编码传 "paragraph_leaf"；
  • render.rs:500-501 —— 传标题 role（h1..h5）。

而 base_leaf（render.rs:422-423）显式写了 let _ = role;，render_card（render.rs:845, 898）同样算出 role 又丢弃。

结论：AI 写的卡片样式 100% 被静默忽略，而且 validate_generated_theme 不会报错。用户看到的现象是「AI 排版好像没什么用」——这不是模型不行，是渲染器没接。

方案：五层表达力，分三步上

第 1 步（1-2 天，收益最大）：把 role 接通

删掉两处 let _ = role;，让 base_leaf / render_card 真正读 theme.blocks；把 render_quote / render_code / render_table / render_list / render_figure / render_toc 全部接进 css(ctx.theme, role, defaults)。这一改，AI 立刻能控制引用、代码块、表格、列表、卡片、图注的边框、圆角、内边距、背景、字号、字重、字色——版式自由度直接上一个数量级。

第 2 步（3-5 天）：单一常量表锁死契约

现在「提示词教一套、渲染器认另一套」是必然事故。做法是引入一张 ROLES: &[RoleDef] 常量表（id + 中文名 + 作用说明 + 该 role 允许的 CSS 属性白名单），然后：

  • css() 的实参从这张表取；
  • AI 提示词由这张表生成（不再手写）；
  • validate_generated_theme 对「表里没有的 role」和「属性白名单外的声明」直接报错。

这样契约在编译期就不可能漂移——和项目已有的 tool_surface_matches_agent_card 漂移测试是同一个思路。

第 3 步（1-2 周）：从「静态样式表」升级到「变体 + 内容感知」

真正的「AI 按语义自由决定版式」需要再加三层。建议的数据结构（TOML）：

# 变体：同一角色多套候选，AI 按内容特征挑
[block.quote]
variant = "card"        # card | plain | big-centered | sidebar

[block.quote.variants.card]
border-left = "3px solid {accent}"
background = "{accent_soft}"
padding = "12px 16px"

[block.quote.variants.big-centered]
font-size = "20px"
text-align = "center"
color = "{text}"

# 内容感知规则：按块的长度/类型/位置自动命中变体
[rules]
quote_short = { when = "chars < 40", use = "big-centered" }
quote_long  = { when = "chars >= 40", use = "card" }
table_wide  = { when = "cols >= 4", use = "scroll" }
first_para  = { when = "index == 0", use = "lead" }

# 局部覆盖：AI 可对单个块指定内联样式（受属性白名单约束）
[override.3]
background = "{accent_soft}"

对应地，AI 提示词从「填色板」变成「先读文章结构摘要，再为每个块选变体」——这才是「AI 排版」而不是「AI 配色」。渲染侧需要把 Block 的元信息（字符数、列数、索引、嵌套深度）暴露给规则层，这部分 IR 已经具备（ir.rs 的语义块自带类型），改造成本可控。

顺便修掉的一个连带问题

theme.rs:88-152 的 Theme::role_style / default_role_style 是死代码（只有测试引用），真正生效的是 render.rs:74 里重写的一份 css()。两套实现分叉，改一处不会同步。做第 1 步时必须一并收敛成一份，否则后面越改越乱。

验收标准
  • 写一份只含 [block.card_note] 的主题，能肉眼看到卡片样式变化（当前是零变化）；
  • AI 生成的主题里，未被渲染器消费的 role 会报错而不是静默通过；
  • 同一篇文章用「变体规则」能产出两种明显不同的版式，且都过 validate --strict。

  2. 修竞态：ai-jobs.js 改为「先注册 handler 再 start」，或让后端在 spawn 之前先 emit 一个 status 兜底。
  3. 修 job 泄漏：jobs.rs:60 用 catch_unwind 包住 work，并把清理逻辑放进 Drop，保证 panic / 提前 return 都清理注册表。

问题五 · 一键复制 / AI 主动推送，粘到公众号就可用 复制这一跳已经通了，主动推送还差 3-4 步人工
现状判定

「一键复制零失真」这条链路的引擎侧是真的通的：copy 走 parse → render(主题) → 图片管线 → normalize → validate → 剪贴板，且带 I-03 阻断。这是产品最有说服力的部分。

但两个关键断点：

方案
  1. AI 回复动作行加「复制富文本（方言）」，直接复用顶栏的 copy_rich。这是投入产出比最高的一改——一行按钮，打通你的核心诉求。
  2. 加「推送到草稿箱」动作，复用 wx_push_draft，并在调用前先跑一遍 I-03 门禁（见问题四）。
  3. 把「主动推送」做成 job：kind="publish"，这样它有进度、可取消、有失败原因，而不是一个会卡住的同步按钮。推送前必须过 blocking_violations 空 + I-03 通过两道闸。
  4. 补 author / digest：从文章 frontmatter 读，不再恒空串。
  5. 群发（publish）保持人工闸门，但要把门禁做真：当前 main.rs:804-815 只检查字符串 --yes，而 agentcard.rs:66 又把这条命令原文写进给 Agent 的卡片——等于教 Agent 去按这个开关。建议：agent card 里移除 publish 示例，改为「群发须由人类在 GUI 内二次确认」。
验收标准
  • 在 AI 对话框里聊出一篇文章 → 点「复制富文本」→ 粘进公众号编辑器样式完整；
  • 点「推送到草稿箱」→ 公众号后台出现草稿，作者/摘要/封面正确；
  • 含本地图的文章点推送 → 被拒绝并提示，而不是推一个必挂的草稿。

路径成熟度还缺什么
CI / 脚本（CLI + JSON）可用但不合格doctor 恒返回 0，无法做前置门禁；不检查 AI Provider。修法：任一 err 时返回非 0。
MCP（Claude / Cursor / VS Code / OpenCode）可用但面窄工具面缺 4-6 个（见问题三）；install 无 --dry-run，CI 里没法「产出配置再分发」；缺 Claude Code 的 .mcp.json 及 Codex / Windsurf / Cline / Zed。
远端服务器 / SCP基本可用单二进制 + 无 daemon + 无自启，天然适合丢上服务器跑。WXWRIGHT_MP_APPID/SECRET 环境变量覆盖已支持（lib.rs:38-46），publish 强制 --yes。补 doctor 退出码即可闭环。
移动端 / 其他设备架构已预留PRD §3.6 规划了 wxwright-ffi 暴露 C ABI。但从投入产出看，先做「CLI 上服务器 + 响应式导出页」比做 App 便宜一个数量级，且能覆盖 80% 的移动端需求（预览 + 分享）。
方案
  1. 修 doctor 退出码：算出 problems 就 Ok(1)；增加 AI Provider、themes/articles 目录写权限、keyring 可用性三项检查。这是 CI/SCP 接管的唯一前置条件。
  2. 给 mcp install 加 --print / --dry-run，让 CI 能产出配置片段而非直接改用户机器；补 Claude Code / Codex / Windsurf / Cline / Zed 目标。
  3. 把 --official-check 做成真执行（当前只 which("node") 打印说明）。CI 里已经在跑真校验器，把这条能力也暴露给 CLI，就能在 SCP 场景下做本地真值门禁。
  4. 补发布产物的签名与校验：PRD 承诺的 minisign / sigstore 未落地，release 只有 sha256sum。做开源分发这是 blocker。
  5. 明确「多渠道」的真实边界：小红书 / 知乎没有个人发文 API，Instagram 卡在公网图片 URL，Facebook 需企业验证。建议把 README 的「7 平台分发」诚实收缩为「1 平台真投递 + 6 平台预览/导出」，用诚实换信任。
验收标准
  • wxwright doctor 在缺凭据时返回非 0，CI 里能作为前置 gate；
  • 一条 GitHub Actions workflow 能完成「拉取文章 → convert → validate --strict → draft create」，无人值守；
  • wxwright mcp install --target claude --print 输出可复制的配置 JSON。

05技术方案汇总

图纸一 · 主题系统 v2（解锁 AI 排版）

06路线图建议

三阶段，按「信任 → 能力 → 留存」排序。核心取舍原则：先把承诺变成真的，再谈新功能。

阶段一 · 止血与信任（最高优先，零新功能）

  1. 修 AppSecret 外泄：把 secret/access_token 从 URL query 挪走，或在 ureq_err 里剥离 query 再进错误串。这是唯一能导致用户公众号被接管的 P0。
  2. 三个回退文件统一 0600 权限（settings.json / config.toml / social-bindings.json），并文档化 Windows 差异。
  3. 补 cache-bust 3 处（app.js → v25、pet.js / ai-jobs.js → v20），加 pre-commit 校验脚本。
  4. 修 doctor 退出码，让 CI/SCP 能真正接管。
  5. 补 GUI 推草稿的 I-03 门禁，消除「会带病上线」的缺口。
  6. 拉官方仓库全集补 R-4.4，闭合「全量规则引擎」这个宣称。

取舍：这一阶段一个功能都不加。README 里承诺过的，必须先是真的。

阶段二 · 解锁核心能力

  1. 主题系统 v2 第 1-2 步：接通全部 role + 单一常量表锁契约。这一步直接决定「AI 排版」是真的还是营销话术。
  2. 平台描述符收进行为 + CLI --platform + MCP wxwright_export。
  3. AI 对话并入 job 运行时，删 7 个死命令，修 handler 竞态与 job 泄漏。
  4. AI 回复加「复制富文本 / 推草稿」，打通「聊完即粘贴」那一跳。
  5. MCP 补 article_read / article_save / fix / draft_update。
  6. 图片三件套：token 重试下沉、内容哈希缓存、云端生图尺寸归一化。

取舍：这一阶段做完，「AI 自主排版 + 一键推送 + Agent 自主操作」三件事才算真的成立。

阶段三 · 兑现分发与留存

  1. X / LinkedIn 投递层（凭据与 OAuth 已就绪，复用骨架即可）——把「真分发」从 1/7 提到 3/7。
  2. 主题系统 v2 第 3 步：变体 + 内容感知规则 + 局部覆盖，实现真正的「AI 按语义决定版式」。
  3. 公式 KaTeX→PNG 落地，补上技术写作者这一块。
  4. 发布工程收尾：minisign / sigstore 签名、非官方免责声明、商标近似性复核归档、CI 加性能回归与 locale parity 门禁。
  5. 变现探索：主题市场改「免费索引 + 付费精品包」——这是唯一与 MIT/Apache 许可不冲突的路径。

取舍：Facebook / Instagram 暂缓（外部依赖最重、产出最差）；GUI 的工坊与宠物停止加功能——它们对「Agent 排版基础设施」这个定位零贡献。
